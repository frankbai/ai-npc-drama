# 架构说明

## 一句话

**三层：宿主（游戏一侧）、NPC 运行时（不认识具体游戏）、内容包（人物和剧情）。** 运行时只负责"让一个有设定、有秘密、有记忆的人物和一个玩家说话"；剧情走到哪、发生了什么、谁什么时候能出场，都是宿主告诉它的。

```
┌───────────── 宿主 host/（Demo 里模拟"游戏服务器"）─────────────┐
│ story.py  剧情导演：章节、CG、事件、线索、变量、预算、指认、结局 │
│ server.py HTTP 接口、页面、口令、限流、用量                      │
└──────────────┬──────────────────────────────────────────────────┘
               │ set_stage / ingest / remember / plan_life
               │ open_session / open_scene / say / compose_line
┌──────────────▼──────── NPC 运行时 npc/ ─────────────────────────┐
│ runtime.py  对话、记忆整理、原话、传话、心声、交情、生活推演      │
│ prompts.py  五种提示词（turn / options / reflect / life / line）  │
│ content.py  读内容包    store.py  存储    gateway.py  模型网关    │
└──────────────┬──────────────────────────────────────────────────┘
               │ 读
┌──────────────▼──────── 内容包 content/ ─────────────────────────┐
│ 运行时读：pack.json、world.md、player.md、npcs/<id>/            │
│ 宿主读：  story/*.json、events.json、clues.json、endings.json    │
└─────────────────────────────────────────────────────────────────┘
```

换一个游戏：内容包换掉；宿主换成你自己的游戏服务器；运行时不动。

## 运行时的接口

宿主能做的事只有这些（`npc/runtime.py`）：

| 方法 | 作用 |
|---|---|
| `register_player(name, shop, gender)` | 新玩家。每个玩家有自己的世界：所有记忆都以玩家为键 |
| `set_stage(player, n, info)` | 玩家进入第 n 个阶段。`info` 里是给 NPC 看的阶段说明：`label`、`gap`、`npc_stage`（每个 NPC 这一阶段和玩家的关系） |
| `plan_life(player, npc, anchor)` | 按剧本锚点推演 NPC 这一阶段的生活；失败就用锚点里的兜底 |
| `ingest(event)` | 世界上发生了什么：`note`（只有玩家知道，写进手记）、`heard`（某个 NPC 听说了，带来源和可靠程度）、`news`（消息，可以是全服的） |
| `remember(player, npc, text)` | 把一段"发生过的事"直接写进 NPC 的记忆，比如写死的 CG |
| `open_session(player, npc, round_limit, situation, arrive, place, total_limit)` | 自由对话。`round_limit` 是和这个人的轮数，`total_limit` 是几个人共用的轮数。每一轮都会重新检查，用完时抛 `Closed`，不调用模型 |
| `open_scene(player, npc, spec)` | 导演场景：场景、必经事件、关键台词、轮数 |
| `say(session, kind, text)` / `close_session(session)` | 说话（流式返回）、结束（结束后整理记忆） |
| `compose_line(player, npc, slot, instruction, before, topics, reveal)` | 专属台词：按指示从记忆里写一句，结果缓存 |
| `view(player, npc)` / `bond_history(player, npc)` | 心智面板、每个阶段交情的起点/最高点/终点 |
| `inner_visibility(player, npc)` | 心声现在给不给玩家看 |

运行时不知道"章节""CG""线索""结局"是什么。

## 一轮对话

1. 宿主调用 `say`。
2. 运行时拼提示词，顺序是：
   - 固定的部分：对话规则、世界、人物本。这部分不变，能吃到提示词缓存。
   - 会变的部分：已解锁的心事、这段时日的生活、近来的消息、眼前这个人（玩家介绍、这一章的你们、交情、看法、事实、往事、约定、讲过的事、听说的事）、这次见面的补充说明（或者导演场景的说明），最后是剩余轮数。
3. 一次流式调用。模型先写一个〔表情〕，再写对白，然后写 `<<<`，最后写一行状态 JSON：交情变化和理由、心情、心声、要不要结束、导演场景里哪些必经事件已经发生。
4. 对白边生成边推给页面；状态 JSON 用来更新交情、记录交情曲线、推进必经事件。
5. 再用一次快模型调用生成回复选项。选项按玩家人设写，人设也按阶段解锁。

## 记忆整理（谈话结束后）

一次调用，输出：
- 日记（带重要度）、对玩家的看法、关于玩家的事实、新约定和已兑现的约定、讲过的事；
- **原话**：玩家说过、值得记很久的话，按话题标注。运行时会核对原文，没有真的出现在这次对话里的句子一律不收，防止模型"记错"；
- **转告**：按 `npc.json` 里 `relays` 写的习惯，把这次听到的事转告给别的 NPC。运行时写进对方的"听说"，来源写"某某（转述）"，可靠程度按配置。

整理失败不会丢数据，下次会自动补做。正在说话时结束会话（比如玩家切了存档），会等这一句说完再整理。整理只改看法、事实和见面次数，不碰信任和亲近，免得把刚涨的交情覆盖回去。

## 分层心事与"真相"

`secret.md` 按 `## 影子`（一直给）、`## 第N章起`（到第 N 章才给）分段。没给的部分模型根本不知道，所以不可能说漏。

`## 真相` 一段只在 `compose_line(..., reveal=True)` 时给模型，用于结局揭晓的那一句。自由对话里永远不会出现。凶手类角色可以这样写：心事里写"无辜版"的说法，也就是他做过的每个动作都有一个说得通的、清白的理由；真相留到揭晓时再给。`tools/check_content.py` 会检查这一点。

## 存储

`npc/store.py`：SQLite（默认，数据在 `local-data/`）和 PostgreSQL（设置 `DATABASE_URL`）两套实现，SQL 一样。主要的表：

| 表 | 内容 |
|---|---|
| `players` | 玩家：名字、据点名、性别、阶段 |
| `bond` / `bond_log` | 交情（信任、亲近、看法、事实）；每个阶段交情的起点、最高点、终点 |
| `episodes` / `commitments` / `told` / `heard` / `quotes` | 日记、约定、讲过的事、听说的事、原话 |
| `journal` / `news` | 玩家手记、消息（`player` 为空表示全服） |
| `life` | 每个 NPC 在每个玩家世界里、每个阶段的生活 |
| `sessions` / `messages` / `lines` | 对话、消息、专属台词缓存 |
| `calls` | 最近 300 次调用的完整提示词（调试用） |

宿主自己的表（`host/story.py`）：`story_progress`（章节、CG 播到哪、导演卡选了哪个版本、指认结果）、`story_vars`、`story_clues`、`done_events`、`player_meta`。

## 并发

- 同一个玩家的记忆整理、生活推演排队做，不同玩家互不等待。
- 宿主那边（`host/story.py`），同一个玩家的推进章节、做事件、指认、开始谈话也排队做。连点两下不会做两遍；CG 推进时页面会带上"我以为自己在第几段"，对不上就不推进。
- 正在进行的谈话存在数据库里（`sessions.ended` 为空的那一条），服务重启后页面刷新还能接着聊、接着演。

## 模型网关

`npc/gateway.py` 只依赖两个能力：流式文本、JSON 对象输出。不用任何厂商独有的功能，换模型只需要改配置。读响应时的网络错误、返回的不是 JSON 对象，一律转成 `ModelError`；运行时对模型输出的每个字段都先检查类型再用。`MockGateway` 是离线模拟，测试和"只看流程"时用。

## 放进真实游戏

1. **宿主换成你的游戏服务器。** 你的服务器在合适的时机调用运行时：玩家推进剧情时调 `set_stage`，游戏里发生了事情时调 `ingest`，打开对话界面时调 `open_session`，播剧情时调 `open_scene` 或 `compose_line`。`host/story.py` 是一个现成的参考实现，演示了章节、事件、线索、结局怎么翻译成这些调用。
2. **存储换成你的数据库。** 实现 `Store` 的那几个方法即可。并发高的话，把 SQLite 换成 PostgreSQL 或者你们自己的存储，并且给每个玩家的写入排好队。
3. **内容包交给策划写。** 人物本、心事、章节都是 Markdown 和 JSON；写完跑 `tools/check_content.py`。
4. **注意成本和延迟。** 每轮 2 次调用。回复选项可以换成更便宜的快模型（`NPC_FAST_MODEL`）。记忆整理和生活推演都在后台做，不阻塞玩家。

## 设计上的取舍

- **每个玩家一个世界。** NPC 对不同玩家的记忆互不相通，避免一个玩家的话被另一个玩家"套"出来。需要全服共享的东西，比如活动、榜单、传言，走 `news`（`player` 为空）。
- **剧本定锚点，模型填细节。** 关键剧情写死，或者用导演卡规定必经事件；模型只负责"怎么说"。推理类剧情的关键线索一律由剧本给，模型只能复述玩家已经拿到的线索，保证推理是公平的。
- **限制模型能知道的，而不是要求模型别说。** 与其在提示词里写"不要说出 X"，不如让提示词里根本没有 X。
